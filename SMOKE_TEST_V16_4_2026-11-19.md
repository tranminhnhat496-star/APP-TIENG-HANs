## 2. Bugs found during the build

- **B-32-1 (build-script assert bug, fixed):** `build_v32.py` step-5
  asserted `bad-version` ×1 in the built file, but the true count is
  ×2 (guard + `v32.js` header comment). The build died at that assert
  after a complete, correct assembly. Fixed by correcting the assert
  to ×2 with the guard text ×1 — `build_v32.py` (step-5 assert) and

- **B-32-2 (PRODUCT BUG, found by `test32.js` §8, confirmed in real
  Chrome — NOT fixed in this build):** the Data Management panel
  renders `#v31panel` ×2 and `#v32monitor` ×2 on every render.
  Root cause: each layer's `wrapDataPanel` guards idempotence with
  only its own marker — `src/v31.js:554`
  (`if(v.dataPanelHTML.__v31)`) and `src/v32.js:394`
  (`if(v.dataPanelHTML.__v32)`) — but the other layer's wrapper does
  not carry that marker. Both layers register a DOMContentLoaded
  re-init (`src/v31.js:661`, `src/v32.js:506`; readyState is
  `'loading'` while the inline scripts parse), so `init31` + `init32`
  run a second time after load, in that order, and each re-wraps:
  the chain becomes v32∘v31∘v32∘v31 and every `dataPanelHTML()`
  call appends the V31 section and the V32 monitor twice.
  Minimal repro (Node vm, real layers): load `v20_sync.js`, `v31.js`,
  `v32.js`, render once (1/1), call `__v31._test.init()` +
  `__v32._test.init()`, render again (2/2, persists on further
  renders). Real-Chrome confirmation: `verify-v32c.js` V32-A —
  `#v31panel` ×2, `#v32monitor` ×2 on first panel render and after
  re-render, in two independent driver runs. Impact: duplicated
  sections + duplicate element IDs in the panel; monitor content
  itself is correct and the cleanup button works. No data loss
  (render-only; no storage writes on the wrap path).
  **FIXED 2026-11-19 by `tools/v32/fix_b32.py` (V32-only, `v31.js`
  untouched):** the V32 wrappers in `src/v32.js` now carry BOTH
  markers (`nw.__v31 = true` AND `nw.__v32 = true`). Verification
  showed the overlap is THREE functions, not one: V31 also wraps
  `__v21.openAccount` / `__v21.closeAccount` (`v31.js:623`), and V32
  wraps the same two — so all three V32 wrappers got the dual marker.
  V32's other wraps do NOT overlap (global `save` — only V20 wraps
  it, and V32 already copies the `__v20` marker; `__v20.flush` —
  V31 never wraps it; `__v31.recordBackupEvent` — V31 defines it,

- **B-32-3 (PRODUCT BUG — V16.3 F-02 fix incomplete on the
  account-switch path, found by `verify-v32c.js` V32-D, NOT fixed in
  this build):** the F-02 account-switch race still loses 3/3 in the
  real Chrome engine. Protocol (same as the V16 baseline R1):
  fresh seed XP 1000, `S.xp += 5; save()` (dirty confirmed), then
  `__v21._test.activateGuest()` within ~5 ms; after reload XP is
  1005 (the stale in-memory save) instead of the switched guest XP
  (9201/9202/9203). Reproduced 3/3 in two independent driver runs
  (6/6 total); the v15 path is 0/3 lost and the v20 path 0/3 lost in
  the same runs, so the harness and the race setup are sound.

## 3. Save-wrap decision (implemented — verified viable in source)

The pre-save guard wraps the global `save`. Verified before wrapping:
V6 HTML:947 declares `function save(){...}` at top level inside the
classic `<script>` that opens at line 877, so `save` IS a plain window
function. V20 `init20()` (`src/v20.js:417`, runs once at V20 load,
before V32) had already wrapped it into a debounced `requestSave()`
wrapper marked `__v20`; V20's `flush()` calls its captured original
save, NOT `window.save`, so the V32 wrap cannot re-enter `flush()`.
The V32 wrapper calls the original FIRST, then schedules
`checkBudget()` after 900 ms (past the V20 800 ms debounce), copies
the `__v20` marker onto itself (so a hypothetical later `wrapSave()`
call sees `__v20` and returns), and never blocks, delays, or alters
the save. Behavioural proof (wrap called exactly once per `save()`
call, data untouched) is asserted by `test32.js` §8 (all three runs:
saveWrapped/flushWrapped true, original called exactly once per call
at ok / 89.9% / past-90% totals, `[V32]` warning logged at warn and
critical) and by real Chrome (`verify-v32c.js` V32-C: badge at
78.3% warn, dismiss works, `[V32]` warn logged).
